## 1. What are SSIT tests?

**SSIT** stands for **Software System Integration Test**. These are end-to-end tests that verify the entire running application — the WPF host window, the Angular UI inside it, and the messages flowing between them — all at once.

Think of it this way:

| Test type | What it tests | Example |
|---|---|---|
| Unit test | One function in isolation | `TranslationService.Resolve()` returns correct string |
| Component test | One Angular component in isolation | Button renders label correctly |
| **SSIT / Integration test** | The whole running app as a user would see it | "When I click Proceed on Introduction, does the Verify Prerequisites screen appear?" |

The SSIT tests in this project **do not mock anything**. They talk to the real app running in the real WPF window.

## 2. How the whole system fits together

Here is what exists at runtime during a test:

```
┌─────────────────────────────────────────────────────┐
│  GuidanceHost.exe  (WPF app)                        │
│                                                     │
│  ┌──────────────────────────────────────────────┐   │
│  │  WebView2  (Chromium browser, embedded)      │   │
│  │                                              │   │
│  │  Angular app  (https://app.local/index.html) │   │
│  │  — renders the 6-step GuidanceUI UI              │   │
│  └──────────────────────────────────────────────┘   │
│                                                     │
│  WPF backend sends messages to Angular:             │
│    ShowSystemLanguage { Language: "English" }       │
│    ShowInstallationPrerequisite { Status: "OK" }    │
└──────────────┬──────────────────────────────────────┘
               │  Chrome DevTools Protocol (CDP)
               │  port 9222
               ▼
┌─────────────────────────────────────────────────────┐
│  Test runner  (dotnet test)                         │
│                                                     │
│  Playwright connects via CDP → controls the         │
│  Angular page as if it were a user                  │
│                                                     │
│  Reqnroll reads .feature files → maps each          │
│  Gherkin line to a C# method → runs it              │
└─────────────────────────────────────────────────────┘
```

**CDP (Chrome DevTools Protocol)** is the same protocol your browser uses when you open DevTools. Playwright uses it to read the DOM, click elements, and read attribute values — all programmatically.

The WPF host is launched with a special flag:
```
WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9222
```
This tells the embedded Chromium to open port 9222 so Playwright can connect.

## 5. How a test run actually works — step by step

When you run `dotnet test`, this is the exact sequence for **every single scenario**:

```
1. Reqnroll reads the .feature file
   └── finds a Scenario, e.g. "Introduction screen is visible"

2. AppLifecycle.[BeforeScenario] fires  (AppLifecycle.cs)
   ├── Creates a Playwright instance
   ├── Connects to GuidanceHost via CDP at http://127.0.0.1:9222/
   ├── Navigates to https://app.local/index.html
   ├── Waits for Angular translations to resolve
   ├── Detects language (English or German) from the DOM
   └── Loads the correct i18n JSON file into PageContext.Translations

3. The Background step runs  (if the feature has one)
   └── e.g. "Given the app is running and the introduction screen is visible"
       → this is a C# method that waits for the introduction screen

4. Each scenario step runs in order
   └── e.g. "Then the element "introduction-screen" is visible"
       → calls ThenElementIsVisible("introduction-screen") in SharedSteps.cs
       → Playwright checks the DOM

5. AppLifecycle.[AfterScenario] fires
   └── Disconnects from CDP (does NOT close GuidanceHost)

6. Repeat from step 2 for the next scenario
```

The key insight: **every scenario starts fresh** — Playwright reconnects and re-navigates to the intro screen. This is why every scenario's Background step navigates to the right screen before assertions start.

## 6. The BDD language — Gherkin

Gherkin is just English with a small set of reserved keywords. You write it in `.feature` files.

### The keywords

| Keyword | Meaning | When to use |
|---|---|---|
| `Feature:` | Names the file/feature area | Once at the top of each file |
| `Background:` | Steps that run before EVERY scenario in the file | For navigation / setup common to all |
| `Scenario:` | One test case with a fixed set of steps | When the test has no varying data |
| `Scenario Outline:` | A template for multiple similar tests | When you test the same thing with different values |
| `Examples:` | The data table for a Scenario Outline | Follows a Scenario Outline |
| `Given` | Sets up the starting state | "The app is on the Introduction screen" |
| `When` | The action the user takes | "The user clicks Proceed" |
| `Then` | The assertion — what should be true | "The Verify Prerequisites screen is visible" |
| `And` | Continues a Given/When/Then | Avoid repeating Given/When/Then on consecutive lines |
| `@TagName` | Labels a scenario for filtering | `@TC01`, `@VVP-A01` |
| `#` | A comment — ignored by the test runner | Documentation inline |

### A minimal example

```gherkin
Feature: Introduction Screen
  The first screen shown when the app launches.

  Background:
    Given the app is running and the introduction screen is visible

  @TC01
  Scenario: Introduction screen is visible
    Then the element "introduction-screen" is visible
```

Reading this out loud: "Given the app is running and the intro screen is visible, then I expect the element with ta-id `introduction-screen` to be visible."

### Scenario Outline — testing multiple values

Instead of writing 6 identical scenarios for 6 different texts, you write one template:

```gherkin
@TC02 @TC03 @TC04 @TC05
Scenario Outline: Introduction screen displays the correct static text
  Then the element "introduction-screen" contains i18n text "<key>"

  Examples:
    | tag  | key                      |
    | TC02 | introduction.title       |
    | TC03 | introduction.description |
    | TC04 | introduction.info        |
    | TC05 | common.copyright         |
```

Reqnroll runs this **4 times**, substituting `<key>` with each row's value. The `tag` column is just documentation — it's not used by the runner. Each row becomes a separate test case.

## 7. Writing a feature file

### The anatomy of a feature file

```gherkin
Feature: [Screen Name]            ← What area of the app this covers
  [One-paragraph description]     ← Context, optional but recommended

  Background:
    Given [navigate to this screen]  ← Runs before EVERY scenario below

  # ── Section heading ────────────────────────────────────────────────────
  # (Comments are just for organisation — the runner ignores them)

  @[TAG]
  Scenario: [Sentence describing what this test checks]
    [Given / When / Then steps]
```

### Tag naming convention

Tags serve two purposes:
1. **Identification** — so you can run just one test with `--filter "TestCategory=TC01"`
2. **Documentation** — so someone reading the feature can cross-reference a requirements list

The project uses these prefixes:

| Prefix | Meaning | Example |
|---|---|---|
| `TC` | Introduction screen tests | `@TC01` |
| `GO-` | Guidance Overview stepper | `@GO-A01` |
| `VVP-` | Verify Prerequisites | `@VVP-B02` |
| `VRS-` | Verification Result (success) | `@VRS-C07` |
| `VRE-` | Verification Result (error) | `@VRE-D14` |
| `SPI-` | Save Patient Images | `@SPI-A01` |
| `DTP-` | Drive To Park Position | `@DTP-B02` |
| `IIP-` | Installation In Progress | `@IIP-C05` |

The letter after the prefix is the **section** (A=presence, B=content, C=buttons, D=navigation). The number is sequential within the section.

### File organisation pattern

Every feature file in this project follows the same sections:

```
A — Screen presence (is the screen visible?)
B — Static content (do the right texts appear?)
C — Buttons / controls (visible, correct color, correct label)
D — Navigation (does clicking X go to screen Y?)
E — Additional sections as needed
```

## 8. Writing step definitions (C#)

A step definition is a C# method with a Reqnroll attribute that tells Reqnroll which Gherkin text maps to it.

### The binding attribute

```csharp
[Then("the element {string} is visible")]
public async Task ThenElementIsVisible(string taId)
{
    await Expect(_ctx.Page.GetByTestId(taId))
        .ToBeVisibleAsync(new() { Timeout = 10_000 });
}
```

- `[Then("...")]` — the Gherkin text pattern. Use `{string}` for quoted parameters, `{int}` for integers.
- The method name is just documentation — it doesn't matter to Reqnroll.
- `async Task` — all Playwright calls are async, so all step methods must be `async Task`.

### The three parameter types

```gherkin
Then the element "proceed-btn" is visible         → {string} → string taId
Then exactly 6 stepper items are rendered         → {int}    → int count  
Then the element "x" has attribute "color" equal to "primary" → two {string}s
```

### The class structure

Every step definition class:
1. Is annotated with `[Binding]` — tells Reqnroll this class contains steps
2. Has a constructor that takes `PageContext` — Reqnroll injects it automatically
3. Contains only `async Task` methods

```csharp
[Binding]
public sealed class IntroductionSteps
{
    private readonly PageContext _ctx;  // injected by Reqnroll

    public IntroductionSteps(PageContext ctx) => _ctx = ctx;

    [Given("the app is running and the introduction screen is visible")]
    public async Task GivenIntroductionIsVisible()
    {
        await Expect(_ctx.Page.GetByTestId("introduction-screen"))
            .ToBeVisibleAsync(new() { Timeout = 10_000 });
    }
}
```

### PageContext — the shared state object

`_ctx` (PageContext) is the central object every step uses. It holds:

```csharp
public sealed class PageContext
{
    public IPage Page { get; set; }           // the Playwright page (the browser tab)
    public IPlaywright? Playwright { get; set; }
    public IBrowser? Browser { get; set; }
    public TranslationService Translations { get; }  // loaded once per scenario
}
```

You never create `PageContext` yourself — Reqnroll creates one per scenario and passes it to every `[Binding]` class that asks for it in its constructor.

### The most important Playwright calls

These are the ones used throughout this project:

```csharp
// Find an element by ta-id attribute
_ctx.Page.GetByTestId("proceed-btn")

// Find an element by CSS selector
_ctx.Page.Locator("sh-stepper-item[ta-id='GuidanceAppStepperStep1']")

// Assert the element is visible (waits up to timeout)
await Expect(element).ToBeVisibleAsync(new() { Timeout = 10_000 });

// Assert the element contains certain text
await Expect(element).ToContainTextAsync("Hello", new() { Timeout = 10_000 });

// Assert an attribute value
await Expect(element).ToHaveAttributeAsync("color", "primary", new() { Timeout = 5_000 });

// Assert element is NOT present (count is zero)
await Expect(element).ToHaveCountAsync(0, new() { Timeout = 5_000 });

// Read an attribute value (to assert manually with Assert.AreEqual)
var actual = await element.GetAttributeAsync("label");
Assert.AreEqual("Proceed", actual, "optional failure message");

// Click an element
await element.ClickAsync();

// Wait for a CSS selector to appear
await _ctx.Page.WaitForSelectorAsync("app-verify-installation-prerequisites",
    new() { Timeout = 10_000 });

// Wait for a JavaScript condition
await _ctx.Page.WaitForFunctionAsync(
    "() => !document.body.innerText.includes('introduction.title')",
    null, new() { Timeout = 8_000 });
```

### Timeout values used in this project

| Timeout | Use case |
|---|---|
| `5_000` ms | Button/element expected to already be visible |
| `10_000` ms | Screen transitions, normal navigation |
| `20_000` ms | WPF backend response (backend takes ~10.5 s to respond) |
| `8_000` ms | Waiting for i18n translations to resolve |

## 9. The infrastructure files you must not break

These three files handle everything before and after each scenario. You rarely need to edit them, but you must understand what they do.

### `Support/PageContext.cs`

The shared state bag. One instance per scenario, shared between all `[Binding]` classes.

```csharp
public sealed class PageContext
{
    public IPage Page { get; set; } = null!;        // Playwright page
    public IPlaywright? Playwright { get; set; }
    public IBrowser? Browser { get; set; }
    public TranslationService Translations { get; } = new();  // i18n resolver
}
```

### `Support/AppLifecycle.cs`

Runs automatically before and after every scenario. **You never call it directly.**

```csharp
[BeforeScenario(Order = 0)]
public async Task Connect()
{
    // 1. Create Playwright
    _ctx.Playwright = await Playwright.CreateAsync();
    _ctx.Playwright.Selectors.SetTestIdAttribute("ta-id");  // ← tells Playwright that
                                                             //   GetByTestId() looks
                                                             //   for "ta-id" attribute

    // 2. Connect to GuidanceHost via CDP
    _ctx.Browser = await _ctx.Playwright.Chromium.ConnectOverCDPAsync("http://127.0.0.1:9222/");

    // 3. Get the page (the Angular tab)
    _ctx.Page = _ctx.Browser.Contexts[0].Pages[0];

    // 4. Navigate to the Angular app
    await _ctx.Page.GotoAsync("https://app.local/index.html");
    await _ctx.Page.WaitForLoadStateAsync(LoadState.NetworkIdle);

    // 5. Wait for WPF to send the language
    await _ctx.Page.WaitForFunctionAsync(
        "() => !document.body.innerText.includes('introduction.title')", ...);

    // 6. Detect language, load translations
    var bodyText = await _ctx.Page.Locator("body").InnerTextAsync();
    var language = bodyText.Contains("Einführung") ? "German" : "English";
    _ctx.Translations.Load(language);
}

[AfterScenario]
public async Task Disconnect()
{
    await _ctx.Browser.CloseAsync();
    _ctx.Playwright.Dispose();
}
```

### `Support/TranslationService.cs`

Loads the i18n JSON and resolves keys. Used by step definitions to get the correct string for the active language.

```csharp
// Loads en.json or de.json from Upgrade/src/assets/i18n/
_ctx.Translations.Load("English");

// Returns "Proceed" (English) or "Weiter" (German)
var label = _ctx.Translations.Resolve("common.proceed");
```

### `ImplicitUsings.cs`

These `using` statements are automatically available in **every** `.cs` file in the project. You never need to add them manually:

```csharp
global using Microsoft.VisualStudio.TestTools.UnitTesting;  // Assert.AreEqual etc.
global using Reqnroll;                                       // [Binding], [Given], [Then]...
global using static Microsoft.Playwright.Assertions;         // Expect(...)
```

## 10. i18n — making tests language-independent

### The problem

The Angular app shows text in English or German depending on what the WPF host sends. If your test hardcodes `"Proceed"`, it passes in English but fails in German where the button says `"Weiter"`.

### The solution — i18n keys in feature files

Instead of writing the English text, write the **translation key**:

```gherkin
# BAD — breaks in German
Then the element "proceed-btn" has attribute "label" equal to "Proceed"

# GOOD — works in both languages
Then the element "proceed-btn" has attribute "label" equal to i18n key "common.proceed"
```

### How the key resolves

At runtime, the step definition does:
```csharp
var expected = _ctx.Translations.Resolve("common.proceed");
// English → "Proceed"
// German  → "Weiter"
```

### Finding the right key

Open `Upgrade/src/assets/i18n/en.json`:

```json
{
  "common.proceed": "Proceed",
  "common.cancel":  "Cancel",
  "common.abort":   "Abort",
  "introduction.title": "Software Installation Process",
  "steps.introduction": "Introduction",
  ...
}
```

The key on the left is what you put in the feature file. The value on the right is what gets rendered in English.

### When NOT to use i18n keys

Use a plain string (not an i18n key) when the value is **not a translated string**:

```gherkin
# color is a component attribute value, not a translation
Then the element "proceed-btn" has attribute "color" equal to "primary"

# type is an enum value
Then stepper item 1 has type "active"

# DOM attribute that is always empty string when present
Then the element "GuidanceAppStepper" has attribute "vertical" equal to ""
```

## 11. The ta-id system — how tests find elements

Tests never use CSS classes or element IDs to find things. CSS classes are styling — they can change. Instead, this project uses a dedicated `ta-id` HTML attribute whose **only purpose is to be a test anchor**.

### In Angular HTML templates

```html
<sh-button ta-id="proceed-btn" [label]="'common.proceed' | t" ...></sh-button>
<sh-button ta-id="cancel-btn"  [label]="'common.cancel' | t"  ...></sh-button>
<div       ta-id="introduction-screen" ...>...</div>
```

### In Playwright (C#)

```csharp
// Finds the element with ta-id="proceed-btn"
_ctx.Page.GetByTestId("proceed-btn")
```

This works because `AppLifecycle.cs` tells Playwright upfront:
```csharp
_ctx.Playwright.Selectors.SetTestIdAttribute("ta-id");
```

### How to find a ta-id for an element you want to test

1. Open the Angular component's `.html` file in `Upgrade/src/app/features/[screen-name]/`
2. Look for `ta-id="..."` on the element
3. If there is no `ta-id`, you need to **add one** to the HTML template first

For example, `introduction.component.html`:
```html
<sh-button ta-id="proceed-btn" ...></sh-button>
```
So in your test you write `"proceed-btn"`.

## 12. Complete worked example — adding a brand new test

Let's add a test for a **new requirement**: the Introduction screen must have its wrapper `<div>` tagged with a ta-id.

We will go through every single step.

### Step 1 — Find the ta-id in the HTML template

Open `Upgrade/src/app/features/introduction/introduction.component.html`.

The outer `<div class="content-panel">` has no `ta-id`. We need to add one:

```html
<!-- Before -->
<div class="content-panel">

<!-- After -->
<div class="content-panel" ta-id="introduction-screen">
```

> **Rule:** Never use an existing CSS class as your test anchor. Always add a dedicated `ta-id`.

### Step 2 — Decide what to test

New requirement: "The Introduction screen footer contains the copyright text."

We will write:
- **Tag:** `@TC05` (already exists — we're using `common.copyright`)
- **Scenario:** Screen displays copyright text

Since `TC05` already exists for the copyright key, let's instead write a brand new one: "The Introduction screen title text is correct." Tag it `@TC02` (already exists) — or, for a truly new test, imagine we're adding `@TC_NEW01`.

To keep this self-contained, let's write a completely new scenario for a new requirement:
**"The Proceed button has color `primary`."** — Tag `@TC08`.

### Step 3 — Write the scenario in the feature file

Open `Features/Introduction.feature` and find the button color section:

```gherkin
@TC08 @TC09
Scenario Outline: Action buttons have the correct color
  Then the element "<element>" has attribute "color" equal to "<color>"

  Examples:
    | tag  | element     | color     |
    | TC08 | proceed-btn | primary   |
    | TC09 | cancel-btn  | secondary |
```

This already exists! So TC08 is already covered.

Let's instead add a completely new scenario — **"The Introduction screen wrapper is visible on first load"** — as `@TC_NEW01`:

```gherkin
@TC_NEW01
Scenario: Introduction screen wrapper is visible on first load
  Then the element "introduction-screen" is visible
```

Add it directly below `@TC01` in the feature file.

### Step 4 — Check if a step definition exists

The line `Then the element "introduction-screen" is visible` maps to the pattern:
```
"the element {string} is visible"
```

Open `StepDefinitions/SharedSteps.cs` and look:

```csharp
[Then("the element {string} is visible")]
public async Task ThenElementIsVisible(string taId)
{
    await Expect(_ctx.Page.GetByTestId(taId))
        .ToBeVisibleAsync(new() { Timeout = 10_000 });
}
```

**It already exists.** So we do not need to write a new step definition. The feature file change alone is enough.

### Step 5 — What if the step does NOT exist?

Imagine you need a new step: `Then the screen title reads i18n key "introduction.title"`.

No existing step matches this. You need to add it to `SharedSteps.cs`:

```csharp
[Then("the screen title reads i18n key {string}")]
public async Task ThenScreenTitleReadsI18nKey(string i18nKey)
{
    var expected = _ctx.Translations.Resolve(i18nKey);
    await Expect(_ctx.Page.Locator(".title"))
        .ToContainTextAsync(expected, new() { Timeout = 10_000 });
}
```

Then in your feature file:
```gherkin
@TC_NEW02
Scenario: Introduction screen shows the correct title
  Then the screen title reads i18n key "introduction.title"
```

## 13. Running the tests

### Pre-requisites checklist

Before every test run, verify:

## 14. When a test fails — how to read the error

### Error type 1 — CDP connection refused

```
System.AggregateException: connect ECONNREFUSED 127.0.0.1:9222
```

**Cause:** GuidanceHost is not running, or was started without the `--remote-debugging-port=9222` flag.  
**Fix:** Close and restart GuidanceHost with the env var set correctly.

### Error type 2 — Element not found / timeout

```
TimeoutError: Locator: GetByTestId("introduction-screen") — waiting for visible
```

**Cause:** The element does not exist on the page, or the `ta-id` attribute is wrong.  
**Fix:**  
1. Open the Angular HTML template for that screen
2. Check the `ta-id` value matches exactly (case-sensitive)
3. If there is no `ta-id`, add one to the template

### Error type 3 — Wrong attribute value

```
AssertFailedException: [proceed-btn] expected attribute 'label'='Proceed' but got 'Weiter'
```

**Cause:** You used a hardcoded English string but the app is running in German.  
**Fix:** Replace the hardcoded string with an i18n key:
```gherkin
# Before
Then the element "proceed-btn" has attribute "label" equal to "Proceed"
# After
Then the element "proceed-btn" has attribute "label" equal to i18n key "common.proceed"
```

### Error type 4 — No step definition found

```
Reqnroll: No matching step definition found for:
  Then the screen shows "Hello"
```

**Cause:** You wrote a Gherkin line in a feature file but there is no C# method with a matching `[Then("...")]` attribute.  
**Fix:** Add the step definition method in the appropriate `*Steps.cs` file.

### Error type 5 — Duplicate step definition

```
Reqnroll: Ambiguous step definitions. Multiple step definitions match:
  ThenElementIsVisible (SharedSteps.cs)
  ThenElementIsVisible (IntroductionSteps.cs)
```

**Cause:** Two different C# classes have the same pattern registered.  
**Fix:** Delete one of them. Generic steps belong in `SharedSteps.cs`. Screen-specific steps belong in their own file.

## 15. Rules and conventions used in this project

These are the design rules applied throughout the existing tests. Follow them when adding new tests.

### Rule 1 — One assertion per concern

Do not put all assertions in one giant scenario. Group them by concern (visibility, content, buttons, navigation) and put each group in its own `Scenario` or `Scenario Outline`.

```gherkin
# BAD — mixed concerns, hard to understand what failed
Scenario: Everything on intro screen is correct
  Then the element "introduction-screen" is visible
  And the element "proceed-btn" is visible
  And the element "proceed-btn" has attribute "label" equal to i18n key "common.proceed"
  And clicking Proceed goes somewhere

# GOOD — each concern is separate
Scenario: Introduction screen is visible
  Then the element "introduction-screen" is visible

Scenario Outline: Buttons are visible
  Then the element "<element>" is visible
  Examples: ...

Scenario Outline: Buttons have the correct label
  Then the element "<element>" has attribute "label" equal to i18n key "<key>"
  Examples: ...
```

### Rule 2 — Do not test what Playwright cannot observe

The `Cancel` button sends a `CloseApp` message to the WPF host, which terminates the WebView2 session and drops the CDP connection. There is no way to assert what happened after that from a test. So Cancel navigation is explicitly noted as untestable:

```gherkin
# NOTE: Cancel sends CloseApp to the WPF host which terminates the WebView2 session.
# This drops the CDP connection so the outcome cannot be asserted from the test runner.
# Cancel is therefore covered by unit tests only.
```

### Rule 3 — One CDP connection, one scenario at a time

The test runner is configured in `ssit.runsettings` to run **sequentially** (1 worker). Do not change this:

```xml
<Parallelize>
  <Workers>1</Workers>
</Parallelize>
```

Running tests in parallel would mean two scenarios trying to use the same CDP connection at the same time, which would cause random failures.

### Rule 4 — Generic steps go in SharedSteps.cs

If a step works for any element (any ta-id, any screen), it belongs in `SharedSteps.cs`. Steps that are specific to one screen belong in that screen's `*Steps.cs` file.

### Rule 5 — Never hardcode translated strings

Always use `i18n key` variants for any text that comes from `en.json` / `de.json`. Use plain strings only for fixed values like `"primary"`, `"secondary"`, `"active"`, `"success"`, `"error"`.

### Rule 6 — Mark unimplemented tests with TODO comments

When a test cannot yet be written because the backend feature is not ready:

```gherkin
# TODO: Add VVP-G14 once the WPF backend abort-reset flow is implemented.
#       The correct post-abort behaviour will be defined at that point.
```

Do not write a failing test and leave it failing. A failing test that is "expected to fail" adds noise and erodes trust in the suite.

## 16. Quick reference cheat sheet

### Finding a ta-id
Open the Angular template for the screen:  
`Upgrade/src/app/features/[screen]/[screen].component.html`  
Look for `ta-id="..."` on the element you want to test.

### Finding an i18n key
Open `Upgrade/src/assets/i18n/en.json`.  
Find the English text on the right, note the key on the left.

### Adding a new scenario (checklist)
- [ ] Choose a tag (follow the naming convention for that screen)
- [ ] Add the `@TAG` and `Scenario:` block to the `.feature` file
- [ ] Check whether a matching step definition already exists in `SharedSteps.cs` or the screen's `*Steps.cs`
- [ ] If not, add the C# method with the correct `[Given/When/Then("...")]` attribute
- [ ] Build: `dotnet build ...IntegrationTests.csproj`
- [ ] Run just the new test: `dotnet test ... --filter "TestCategory=YOUR_TAG"`

### Step definition patterns already available (SharedSteps.cs)

| Gherkin pattern | What it does |
|---|---|
| `the element {string} is visible` | Waits for element with ta-id to be visible |
| `the element {string} is not present` | Asserts element with ta-id does not exist |
| `the element {string} is clicked` | Clicks the element |
| `the element {string} contains text {string}` | Assert text is present (hardcoded string) |
| `the element {string} contains i18n text {string}` | Assert text via i18n key |
| `the element {string} has attribute {string} equal to {string}` | Assert attribute = hardcoded value |
| `the element {string} has attribute {string} equal to i18n key {string}` | Assert attribute via i18n key |
| `the element {string} has no interactive button {string}` | Assert button is absent inside element |
